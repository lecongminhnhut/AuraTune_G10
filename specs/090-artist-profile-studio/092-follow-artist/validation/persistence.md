# 092 persistence — local verification

[Accepted physical design](../preparation/accepted-design.md) and [migration 005](../../../../src/database/migrations/005_artist_follows.sql) use the exact supplied pair/FKs/created_at, preserving default NO ACTION deletion. No counter, surrogate/event table, guessed cascade, localStorage import or historic timestamp backfill. Existing nonnull times survive at microsecond precision. NULL history aborts the transaction; future created_at is required. Tests exercise both existing deployed-schema and absent-table installation paths.

The functions are SECURITY DEFINER with empty search_path, fully qualified sources and no PUBLIC/anon/authenticated EXECUTE. Follow table RLS is enabled and browser-role/PUBLIC table privileges are revoked; personal transport is backend-only. Capture existing grants/policies before live rollout; this migration deliberately changes follow-table browser access, not users/artists/auth grants. Service role receives only the two operation function execution grants here. Identity eligibility is reused via 091's filtered view, not reimplemented from role/mock data.

Signed canonical users.user_id maps to the follow owner. Session ownership joins through the corresponding users.id, respecting migration 001 rather than assuming the two values equal. Fixtures deliberately distinguish these IDs. Current account/session rows are share-locked; mutation locks the actual Artist row even when the follow pair is absent. Linked-account eligibility is rechecked and session expiry is checked again after lock waits. Conditional INSERT ON CONFLICT DO NOTHING preserves original time; a new relation uses clock_timestamp after the processing locks. DELETE affects only that owner/Artist. Hidden without own relation and unknown/deleted produce identical generic 404.

SQL list is a single-statement complete JSON aggregate with optional same-snapshot public-target check. It preserves full timestamp precision and bigint-as-text before JSON, sorts time DESC/bigint ID ASC, exposes no hidden totals or account fields, and avoids PostgREST row caps. App-level projection additionally validates/allowlists all fields and image protocols.

Executed: 6 PGlite persistence tests, 1 supplied-schema migration/preflight test (two databases), actual Express tests and 5 independent-connection PostgreSQL histories all PASS. Failed SQL transaction rollback and NULL-preflight rollback are verified. Repeated migration is intentionally not an idempotent deployment mechanism: no history/state is overwritten by CREATE OR REPLACE. No SQL has been applied to Supabase.

Rollout prerequisites: apply 003/004 first; inspect actual users/session/Artist/follow DDL and service-role/PostgREST behavior; run `SELECT count(*) FROM public.user_follows_artist WHERE created_at IS NULL` privately. If nonzero, obtain an authoritative historical source or separately approved treatment; do not guess a date. Execute 005 once through the database change process and refresh PostgREST schema cache if necessary. Before deployment record existing follow grants/policies; rollback requires restoring that captured ACL/RLS/nullability state as well as dropping only the three new functions. Do not drop the existing follow table or restore a stale relationship snapshot as a routine rollback. Function rollback-on-error is tested; full live deployment/ACL restoration is not claimed.
